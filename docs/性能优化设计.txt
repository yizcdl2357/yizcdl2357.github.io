# 英语语料库首页性能优化设计

## 1. 目标与性能预算

目标是在普通网络（移动 4G/家庭宽带、无本地缓存）下，使首页在 **2 秒内可用且完成主要内容渲染**，同时保持现有视觉、功能、API/数据库契约、DDD 分层和部署拓扑不变。

### 预算（暖机请求）

- GitHub Pages TTFB：`<=300ms`（p75）。
- Railway API TTFB：`<=500ms`（p75）。
- LCP：目标 `<=2.0s`，硬上限 `<=2.5s`。
- INP：`<=200ms`；CLS：`<=0.1`。
- 首屏关键资源（HTML、关键 CSS、必要配置与首屏脚本）压缩后目标 `<=250KB`，关键请求数目标 `<=12`。
- 首页首屏只请求当前视图所需数据；语料库、OCR 等非首屏功能不得阻塞首屏。

### 冷启动预算

Railway 休眠唤醒、Node 进程初始化、连接池建立和迁移检查需单独记录。冷启动允许高于暖机目标，但应通过健康检查、受控发布迁移和实例保活将 p95 控制在 `<=4s`；冷启动期间前端显示稳定的加载占位，不改变最终 DOM 结构或数据契约。

## 2. 测量方法

1. 使用 Chrome Performance/Network trace 和 Lighthouse，在 `320/520/820/1280px` 视口分别测量。
2. 每个视口执行两组场景：禁用缓存的首次访问（冷浏览器）和重复访问（暖缓存）；Railway 再分别记录实例冷启动与已唤醒请求。
3. 记录导航、资源、API 请求的开始/结束时间、传输大小、状态码、缓存命中和连接复用情况；服务端仅记录请求 ID、路由、阶段耗时、查询次数与总查询时长，不记录 cookie、令牌或正文。
4. 浏览器通过 `PerformanceObserver` 采集 LCP、CLS、INP，并关联页面请求 ID；服务端通过 `Server-Timing` 或等价响应头暴露解析、业务、数据库阶段耗时（不泄露敏感信息）。
5. MySQL 统计每个 API 的查询数量、单次及总耗时，重点核对段落搜索、标签、作者和收藏数查询。
6. 每个场景至少运行 10 次，比较 p50、p75、p95；优化前后使用同一网络、设备和数据快照，避免只比较单次最好结果。

## 3. 当前首页瀑布流（基线）

```text
GitHub Pages HTML
  -> CSS 与多个 classic JS 顺序下载/执行
  -> runtimeConfig.js（API 客户端依赖它，必须先执行）
  -> 应用启动
       -> /api/auth/me
       -> 首页 /api/paragraphs
       -> 语料库预渲染再次请求 /api/paragraphs（重复工作）
  -> 每个段落追加标签、作者、收藏数查询（潜在 N+1）

Railway 冷启动
  -> Node 进程
  -> 启动时迁移检查
  -> MySQL 连接池建立
  -> API 处理并执行查询
```

基线必须保留为可复现 trace。任何优化都要确认请求顺序、返回 DTO、排序和错误行为没有变化。

## 4. 优化方案

### 4.1 静态资源与传输

- 保持现有 DOM/CSS 视觉契约；仅采用传输层优化，不改颜色、尺寸、排版或交互。
- 对静态文件使用内容哈希/版本化文件名，或配置长期缓存（`Cache-Control: public, max-age=31536000, immutable`）；HTML 使用短缓存并在发布时刷新引用。
- GitHub Pages 与 Railway 均启用 Brotli，不能用 Brotli 时回退 gzip。
- 在 HTML 中对 Railway API 使用 `preconnect`，必要时增加 `dns-prefetch`；只 preload 真正阻塞首屏的 CSS 或运行时配置，避免过度预加载。
- Tesseract 改为仅在用户进入 OCR 功能时延迟加载，不能在首页启动阶段下载或初始化。
- 保留脚本依赖顺序；将非关键脚本移出首屏阻塞路径，并通过 `defer`/模块化加载保证初始化顺序不变。

### 4.2 前端启动与请求

- 启动时只渲染当前激活的首页；用户切换到语料库时再渲染语料库，禁止启动阶段预渲染隐藏页面。
- 为相同参数的 `/api/paragraphs` 建立 in-flight 去重与短时读缓存，避免认证初始化、首页和语料库触发重复请求。
- 缓存内容可先展示再后台刷新；刷新结果必须按请求版本提交，禁止旧响应覆盖新数据。
- 创建、删除、收藏/取消收藏成功后，精确失效段落列表、详情和收藏计数缓存；失败操作不得失效或写入缓存。
- 保持云 API 与本地开发 fallback 的边界：配置云 API 时不得静默切换到本地数据；认证、cookie、CORS 行为保持不变。

### 4.3 API 与 Railway

- 将数据库迁移从每次进程启动的隐式路径移至受控发布步骤；启动时只执行轻量版本检查，避免阻塞首个请求。
- 配置 Railway 健康检查、合理的启动超时和实例保活策略；记录冷启动、连接池创建和首个查询耗时。
- 对公开、幂等的 GET（语料列表/详情）提供极短 TTL 的服务端缓存，并支持 ETag/`If-None-Match` 条件请求；认证和私有数据绝不共用该缓存。
- 保持所有 API 路径、方法、状态码、响应字段、分页和排序完全兼容。

### 4.4 MySQL 查询与索引

- 消除 N+1：段落主查询后，使用 JOIN 或按段落 ID 批量查询一次性取得标签、作者用户名和收藏计数，再在应用层按原顺序组装 DTO。
- 评估并补充以下索引（均为 additive、安全迁移，不改变表/列语义）：
  - `paragraphs(created_at)`
  - `paragraphs(author_id, created_at)`
  - `collections(paragraph_id)`
  - `paragraph_tags(tag_id, paragraph_id)`（现有主键顺序之外）
  - 保留现有唯一键 `(user_id, paragraph_id)`。
- 使用 `EXPLAIN` 验证搜索、分页、标签过滤和收藏计数均命中预期索引；保持原有排序、去重和事务边界。

## 5. 缓存与一致性边界

| 数据/接口 | 缓存策略 | 失效规则 |
| --- | --- | --- |
| 公开语料列表、详情、聚合计数 | 客户端短 TTL + ETag；服务端可短 TTL | 创建、删除、收藏/取消收藏后失效相关列表/详情/计数 |
| `/api/auth/me`、`/api/me/*` | `no-store` | 不进入共享缓存 |
| 登录、注册、登出及所有写操作 | `no-store` | 不缓存请求或响应 |
| 带 cookie、授权头或用户私有字段的响应 | `private, no-store` 或等价策略 | 严禁共享缓存 |

cookie/session 语义、CSRF/CORS 策略和跨设备以云端 MySQL 为权威的规则保持不变。任何缓存键不得包含或输出密钥、令牌、cookie 或其他秘密；ETag 只基于公开响应内容及版本。

## 6. 非变更约束

- 不改变可见 DOM 结构、CSS 计算结果、响应式断点和交互行为。
- 不改变 API 路径、请求参数、响应 DTO、状态码、分页、排序和错误语义。
- 不改变数据库表/列含义、外键和 DDD 依赖方向；索引仅作可回滚的加法迁移。
- 不移除跨设备共享的云端 MySQL，也不在云 API 已配置时静默使用本地 fallback。

## 7. 实施阶段与验收门禁

1. **基线仪表化**：落地浏览器、API、MySQL 分阶段计时，保存冷/暖 p50/p75/p95 trace。
2. **前端请求治理**：去重、短 TTL、按需渲染语料库，延迟加载 OCR；验证视觉快照和 DOM 快照。
3. **API/数据库批处理**：消除 N+1，增加并验证索引；用同一数据集核对 DTO、排序、总数和权限。
4. **缓存与压缩**：启用 ETag、短 TTL、Brotli/gzip 和静态缓存头；执行缓存污染与隐私测试。
5. **冷启动治理**：迁移改为受控发布步骤，配置健康检查/保活并复测 Railway 冷启动。
6. **发布验收**：在四个视口和冷/暖场景下，首页 LCP p75 `<=2.0s`（不得超过 `2.5s`），CLS/INP 达标，关键资源与请求数不超预算；API E2E、CORS/cookie、登录/登出、上传/删除/收藏回归通过，且无响应式横向溢出。

任何门禁失败都必须回到对应阶段定位，不得以关闭功能、改变视觉、放宽 API 契约或启用不透明 fallback 作为“优化”。
